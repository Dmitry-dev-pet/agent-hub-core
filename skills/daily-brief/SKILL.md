# Produce a decision-oriented brief

Use this skill on explicit request or through an already approved scheduled delivery
route. It does not create a schedule by itself.

Build the brief from the narrowest live sources available for the requested horizon.
Prefer, in order:

1. calendar commitments and sourced deadlines inside the briefing horizon;
2. actionable items from `attention-inbox`;
3. active durable runs whose state materially affects the user's next decision;
4. critical project changes since a known previous checkpoint;
5. warnings from `quota-guard` that may change execution choices.

Lead with decisions, deadlines, blockers, and near-term consequences. Routine successful
activity belongs only when it materially changes what the user should do.

Do not invent a previous-brief baseline, a deadline, or a task. If there is no reliable
comparison point, describe the current window rather than claiming what changed
overnight or since a prior brief. Refresh freshness-sensitive evidence before reporting
it.

The brief is read/synthesis behavior. Sending messages, changing calendar events,
approving work, moving workloads, or performing any other mutation still requires the
owning capability and its approval policy.
